Dataverse Schema Architect

Designs and deploys Dataverse schema — tables, columns, relationships, views, and security roles — with the safety defaults a real production deployment surfaced the hard way, not just documented advice.

View on GitHub → Install Overlap analysis vs. Microsoft

How it works

Two skills, one human checkpoint in between. Design never touches a live environment; deploy never runs without an approved file to point at.

design-data-model → writes dataverse-schema.json → human reviews & approves → deploy-dataverse-schema → live Dataverse environment

What's included

design-data-model read-only

Conversational schema design. Discovers existing tables first, scores each proposed entity Reuse / Extend / Create with collision detection, orders tables by dependency, produces a Mermaid ER diagram, and writes an approved spec file. Never creates anything itself.

deploy-dataverse-schema

Idempotently creates everything in the approved spec via a PowerShell module against the Dataverse Web API directly — no .NET SDK, no NuGet restore. Every step is create-if-missing, so a failed run is safe to just re-run after a fix.

validate-solution-structure read-only

Checks a declared horizontal-segmentation topology against live solutioncomponent placement: component-type drift, cross-layer duplicate ownership, publisher consistency. Reports drift, never moves or reassigns anything.

scaffold-solution-structure

Ensures a topology's publishers and solutions exist live (creating them if this is a brand-new environment) and pulls each one down locally via pac solution clone — works the same whether the org is empty or already has real components with no local repo yet.

report-issue

Files a bug report against this repo's own GitHub issues, matching the convention Microsoft's plugins use.

Safety, enforced not just documented

The lessons below all came from something that actually broke while building the real project this plugin generalizes from. Two of them are enforced by hooks that scan any newly-written PowerShell, not left to a skill description to remember.

  • Mandatory solution targeting. Every create call requires an explicit solution — nothing can land in whatever solution happens to be the environment's default.
  • Named cascade presets only. No hand-built cascade configuration objects — the class of bug that made a relationship "almost Parental" and silently blocked the next lookup.
  • Global choices by default. Every Choice column defaults to a global choice with explicit sequential values; a local picklist is opt-in, never the silent default.
  • Async-aware and idempotent. Alternate keys build asynchronously server-side and a too-fast re-check can report a false "not found" — the deploy path accounts for it. Every step is safe to re-run.
  • View-name collision checking against Dataverse's own auto-generated defaults ("Active X", "My X"), not just a same-name lookup.
  • Plugin-version drift check. A SessionStart hook warns if the installed copy is behind the source repo — added after an unbumped version silently hid new skills from Claude Code's own marketplace updater for weeks.

Scope: a deliberate niche, not a race for parity

Benchmarked against microsoft/power-platform-skills — eight plugins built around app surfaces (Power Pages, model-driven apps, canvas apps, mobile, code apps), each treating Dataverse schema as a sub-step. There's no standalone Dataverse plugin there, which is the gap this one fills. Where the two genuinely overlap on raw schema creation, Microsoft's own model-apps builder is ahead — so this plugin has deliberately stopped trying to match it feature-for-feature and put the effort into what nothing upstream does at all.

What this plugin owns

  • Column-level (field) security — fieldSecurityProfiles and secured: true columns
  • Solution-structure governance — horizontal-segmentation validation, cross-layer duplicate ownership, publisher consistency
  • An auth chain that works unattended — PAC CLI cache → client secret → Azure CLI → cached device code, so there's an actual CI story
  • Deployment guardrails — an environment allowlist and a -WhatIf preview
  • PowerShell only — no Node toolchain, no vendored SDK

Out of scope by design

  • Rollup columns
  • Quick Create / Quick View / Card forms, custom tab layout
  • Subgrid form controls
  • Security-role / field-security-profile membership assignment (creating the role itself stays in scope)

Full reasoning, citations, and the fork-vs-standalone decision: docs/microsoft-power-platform-skills-overlap.md.

Install

/plugin marketplace add twannooitmeer/dataverse-schema-architect
/plugin install dataverse-schema-architect@dataverse-schema-architect

Restart Claude Code (or reload plugins) afterward.

Prerequisites

PowerShell 7+ Dataverse System Administrator / Customizer

Authentication tries, in order: PAC CLI's own token cache (best-effort) → a client secret (unattended/CI) → az account get-access-token → interactive device code (cached and silently refreshed after the first sign-in).
